# Реєстр Issue #1 — реалізація та перевірка

Команда: **ITT-Zholudi**.

Реалізацію Issue №1 прийняли в приватній чернетці. Джерело, повторні перевірки й наступний крок описано в [записі етапу 1](stages/01-registry.md).

## Локальний запуск

Node.js 24 та npm, із кореня репозиторію:

```sh
npm ci
npm test
npm run build
DEMO_MODE=true npm run seed
DEMO_MODE=true npm start
```

Відкрити http://127.0.0.1:3001. На Windows PowerShell перед seed/start встановити `$env:DEMO_MODE="true"`.

Для Vite: `DEMO_MODE=true npm run dev:api` та `npm run dev:web`. Дозволені Origin: localhost/127.0.0.1 на портах 3001 та 5173. Мутації без дозволеного Origin відхиляються, включно із запитами через curl. API за замовчуванням слухає лише 127.0.0.1. Довільні хости та CORS не ввімкнені.

Для ізольованого локального набору можна передати `DATABASE_PATH=/абсолютний/шлях/demo.sqlite` обом командам seed і start.

Сервер застосовує `001_registry.sql` транзакційно перед початком прослуховування. Seed запускається явно, лише в DEMO_MODE, і створює весь набір разом із маркером `seed_batches` в одній транзакції. Повтор із тим самим manifest перевіряє UUID/посилання та не змінює даних. Колізія до першого застосування дає `seed_conflict`, відсутній запис після застосування — `seed_inconsistent`, зміна manifest під тією самою версією — `seed_version_conflict`; частковий ремонт відсутній. Зберігаються стабільні UUID, зокрема індикаторів seed. Перед ручним застосуванням міграції до наявної робочої БД зробити резервну копію `data/demo.sqlite`; автоматичного видалення БД немає.

Без `DEMO_MODE=true` демомаршрути повертають 404, доменні маршрути — 401, health лишається публічним. Демосесії — виключно локальна демонстрація на синтетичних даних, без зовнішньої автентифікації. Cookie HttpOnly / SameSite=Strict, TTL 8 годин; у БД лише SHA-256 токена. Відключення користувача перевіряється при кожному запиті. Перемикання користувача анулює попередню сесію поточного браузера.

## Демокористувачі

| Користувач | Доступ |
| --- | --- |
| Виконавець А | Захід M-501; тільки призначені йому записи підрозділу 1 програми DEMO-1 |
| Виконавець Б | Захід M-502; той самий підрозділ, інший власник |
| Виконавець іншого підрозділу | M-503; підрозділ 2 програми DEMO-1 |
| Виконавець іншої програми | M-504; програма DEMO-2 |
| Координатор А | Читає, створює й редагує заходи підрозділу 1 програми DEMO-1 |
| Керівник А | Читання двох підрозділів DEMO-1; без аудиту та запису |
| Аналітик А | Читання підрозділу 1 DEMO-1; без аудиту та запису |
| Адміністратор демо | Читання всіх програм/заходів, аудит і синтетичний імпорт; не редагує заходи |
| Неактивний виконавець | Не показується в меню входу, вхід за UUID відхиляється |

Ідентифікатори доступні у `apps/api/fixtures/registry.json`. Новий захід отримує `effectiveFrom = max(поточна дата Europe/Kyiv, початок програми)`. Після завершення програми створення відхиляється. Для історичного синтетичного імпорту `effectiveFrom` передається явно. Код унікальний у парі розділ/підрозділ; список показує підрозділ.

Активність запису заходу означає включення до реєстру; це не стан погодження результату.

## Ручний сценарій браузера

1. Увійти як **Координатор А**. Перевірити DEMO-1, два початкові заходи та лише підрозділ 1 у формі.
2. Натиснути **Створити захід**. Вибрати розділ 1, виконавця А, унікальний код `DEMO-UI-1`, назву `Навчальна перевірка`, дату не раніше поточної дати за Києвом і в межах програми, назву індикатора, базу 0, ціль 100, напрям «Збільшення». Зберегти.
3. Перевірити картку й рядок у списку. Відредагувати назву; версія має збільшитися. Для розділу 2 форма вимагає ризик; для постійного заходу поле дати приховане.
4. Увійти як **Виконавець А** — новий захід доступний, кнопки створення й редагування відсутні. Увійти як **Виконавець Б** — новий захід відсутній; пряма адреса `/api/measures/<id>` повертає 404.
5. Вибрати для виконавця А розділ 3 — показано порожній стан. Перервати доступ до API й повторити завантаження — показано помилку.
6. У двох вкладках координатора відкрити один захід на редагування. Зберегти в першій, потім у другій — друга показує конфлікт версії та кнопку **Оновити картку**. Вона завантажує актуальну версію; незбережений текст другої вкладки скидається.

**Результат 18.11.2026:** сценарій перевірено в браузері Codex на ізольованій SQLite-базі з Node.js 24.22.3. Координатор А побачив два початкові заходи й лише свій підрозділ у формі, створив `DEMO-UI-1`, змінив назву й дату; версія зросла з 1 до 4. Виконавець А бачив новий захід без кнопки редагування; Виконавець Б бачив тільки M-502. Окремий HTTP-запит під сесією Виконавця Б на id нового заходу повернув 404 `not_found`. Фільтр розділу 3 показав порожній стан. Для розділу 2 форма показала обов’язковий ризик, а для постійного заходу приховала дату. У двох вкладках координатора друга зміна дала 409 із кнопкою «Оновити картку»; оновлення показало версію 3 й відкинуло незбережений текст.

Звичайна зміна дати клавіатурою збереглася. Автоматизована команда `fill` для нативного `input[type=date]` змінювала видиме поле, але не стан React; після наступного вводу попередня дата поверталася. Це обмеження способу автоматизації, а не підтверджений дефект ручного вводу. Під час перевірки виявлено, що стара картка залишалася під порожнім списком після зміни фільтра; форму й картку тепер закрито при зміні розділу. Після повторної збірки браузер показав порожній розділ без старої картки. Стан помилки при недоступному API й адаптивні розміри екрана окремо не перевірено; незалежний рев’юер може доповнити їх. Результат браузерної перевірки не замінює незалежного рев’ю коду та критеріїв Issue #1.

### Перевірка із затримкою відповіді картки

У Chrome під **Координатором А** з ізольованою SQLite-базою та синтетичним seed затримано на 2,5 секунди лише `GET /api/measures/:id`. Після відкриття M-501 і появи повідомлення «Завантаження картки…» вибрано порожній розділ 3. Коли сервер обробив відкладений запит, на екрані залишилося «Доступних заходів: 0», без картки, повідомлення про її завантаження чи помилки.

На зібраному вебінтерфейсі зі штучними відповідями API перевірено п’ять сценаріїв із такою самою затримкою. Для пагінації сценарій використовував 22 заходи, 20 на першій сторінці. Усі перевірки пройшли.

| Дія під час завантаження картки | Результат після затримки |
| --- | --- |
| Вибрати порожній розділ 3 | Список показує 0 заходів, стара картка не з’являється |
| Натиснути «Наступна» й відкрити запис на другій сторінці | Відкривається картка нового запису та залишається видимою |
| Натиснути «Попередня» | Картка з другої сторінки не з’являється |
| Натиснути «Створити захід» і ввести код | Форма створення залишається відкритою та зберігає введене значення |
| Змінити розділ перед відповіддю 503, потім повторити запит без навігації | Помилка скасованого запиту не з’являється, помилка чинного запиту відображається |

Для повторного рев’ю використати затримку тільки для відповіді картки, залишивши список і довідники доступними. Виконати дію під час індикатора завантаження картки й перевірити екран після спливу 2,5 секунди.

## HTTP-перевірки

`npm test` запускає десять груп тестів (health та дев’ять груп реєстру), які перевіряють:

- чисту БД, повторну міграцію/seed і збереження зміненого запису;
- усі п’ять ролей, власника, чужий підрозділ/програму, фільтрацію до pagination/count та підміну ролі заголовком;
- відсутню, прострочену та деактивовану сесію, logout, хешування токена, Origin і вимкнений деморежим;
- створення й частковий PATCH, перевірки календарної дати, ризику, виконавця, цілі, невідомих полів, конфлікту версії та дубліката коду;
- відкат заходу, індикатора й аудиту при штучній помилці запису аудиту;
- перезапуск із вимкненим деморежимом, колізії/відкат seed, точний scope виконавця, незалежність кодів різних підрозділів та незмінний початок дії заходу за датою Europe/Kyiv;
- синтетичний імпорт, його обмеження розміру/кількості, заборону не-admin, повторного пакета, некоректних зв’язків та атомарність при помилках.

## Імпорт і межі

`POST /api/imports/registry` приймає формат із [контракту](registry-contract.md), тільки для admin. `apps/api/fixtures/registry.json` — повний синтетичний приклад; повторне надсилання вже засіяного набору очікувано дає 409. Для нового набору потрібні нові UUID та коди програм. Обмеження: 1 MiB JSON і 1000 записів разом із вкладеними індикаторами. Нові програми містять рівно три розділи. Пакет створює записи та аудит однією транзакцією; оновлення наявних записів через імпорт відсутнє.

[Офіційний синтетичний набір](https://hack.bitec.com.ua/wp-content/uploads/2026/11/zavdannia-2-syntetychnyi-nabir-63022726.zip) доступний. Його архів, словник і поля зіставлено з внутрішньою схемою в [карті відповідності](official-dataset-mapping.md). Прямий імпорт CSV/JSON/XLSX організаторів **не реалізовано й не перевірено**; `POST /api/imports/registry` приймає лише власний формат контракту. UI імпорту/адміністрування, докази, погодження, дашборди та звіти належать наступним задачам. Поточний UI надає список, фільтр розділу, pagination, картку й форму координатора; аудит доступний через API. Після приймання реалізації #1 наступна задача — #2.
