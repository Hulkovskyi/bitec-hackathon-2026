# Результат, докази та погодження

Для запуску використайте [README](../README.md). Виконайте seed і запуск з однаковим `DATABASE_PATH`. Коли він не заданий, база лежить у `data/demo.sqlite`, а докази в `data/demo.sqlite.evidence`. Для власного шляху до бази застосунок додає суфікс `.evidence` до цього шляху. Резервна копія має охоплювати базу та каталог доказів одного стану. Демонстрація використовує лише синтетичні записи й файли.

## Модель, API й доступ

Одноразовий захід використовує ключ `once`, а постійний — `YYYY-H1` або `YYYY-H2`. Міграція 002 додає `results`, `period_assignments`, `evidence_versions` і `result_reviews`. Незавершена ревізія може переходити між станами `draft → submitted → returned → submitted → approved`. Погоджена ревізія зберігається в історії.

| Операція | API |
| --- | --- |
| Чинне призначення за період | `GET /api/measures/:id/assignment?periodKey=…` |
| Перепризначити виконавця | `PUT /api/measures/:id/assignment` |
| Історія перепризначень | `GET /api/measures/:id/audit?entityType=period_assignment&periodKey=…` |
| Переглянути або створити результат | `GET/POST /api/measures/:id/results` |
| Переглянути, змінити або подати результат | `GET/PATCH /api/results/:id`, `POST /api/results/:id/submit` |
| Повернути на доопрацювання або погодити | `POST /api/results/:id/review` |
| Переглянути журнал результату | `GET /api/results/:id/audit` |
| Додати версію доказу, завантажити або перевірити файл | `POST /api/results/:id/evidence`, `GET /api/evidence/:id/download`, `GET /api/evidence/:id/integrity` |

Виконавець бачить доступні йому результати й завантажені ним версії доказів. Координатор повертає або погоджує результати у своєму підрозділі. Запит невідомого чи недоступного результату або файла повертає 404. Мутації перевіряють `version`. Повернення вимагає коментаря. Під час погодження сервер перевіряє цілісність актуальних файлів.

Сервер присвоює кожній версії доказу окремий ключ і записує SHA‑256 разом із метаданими. Локально метадані лежать у SQLite, файли — поза вебкаталогом. Онлайн застосунок використовує PostgreSQL і приватне сховище Supabase. Для PDF, PNG, JPEG і TXT діє ліміт 5 МіБ локально та 4 МіБ онлайн. [Повний контракт](workflow-contract.md#issue-2--результат-докази-погодження)

## Як повторити в браузері

1. Увійдіть як **Виконавець А**, відкрийте **M-501** і створіть чернетку в секції «Результат виконання».
2. Оберіть «Виконано», вкажіть фактичну дату в періоді програми, опис і значення індикатора, наприклад 100. Збережіть. Додайте синтетичний файл TXT та натисніть «Подати на перевірку».
3. Увійдіть як **Координатор А**, відкрийте M-501. Перевірте цілісність файла. Введіть коментар і поверніть результат на доопрацювання.
4. Увійдіть як **Виконавець А**. У поверненому результаті виберіть «Нова версія» для доказу, додайте оновлений файл і подайте повторно. У розділі «Історія версій файлів» можна завантажити початковий файл.
5. Увійдіть як **Координатор А**, перевірте новий доказ і погодьте результат. У журналі змін видно автора, час і деталі змін.
6. Увійдіть як **Виконавець Б**. Перевірте, що M-501 відсутній у списку. Запити чужого результату та файла повертають 404.

## Реалізація і перевірки

- Міграція 002 додає результати за періодом, призначення, версії доказів і рішення. Чинне призначення визначає доступ до поточного заходу, погоджена ревізія має власну історію.
- API синхронізує версії результатів. Запис погодження й аудит фіксуються атомарно. Запит картки координатора повертає `planFrozen`, щоб показати, коли редагування плану заблоковане.
- SHA‑256 обчислюється з оригінальних байтів. API видає дозволені файли як вкладення. Пошкодження файла блокує погодження.
- Під час приймання етапу 2 пройшли `npm ci`, `npm test` (21/21), `npm run build` і `git diff --check` пройшли. HTTP-тести охоплюють цикл погодження, конфлікти версій, відкат аудиту та файлів, перепризначення, пізнє подання за H1 і відмову в доступі до доказів попереднього виконавця.
- У Chrome з Express, ізольованою SQLite-базою та синтетичними TXT пройдено подання, повернення, заміну файла, повторне подання й погодження. Підтверджено SHA-256, завантаження першої версії та 404 під Виконавцем Б. Перевірено вигляд на ширинах 1366 і 390 пікселів.

## Повторне рев’ю · пізнє подання за H1

В ізольованому синтетичному наборі встановіть M-501 як постійний захід із початком 01.01.2026, базовим виконавцем А та `plannedDate=null`. Обидва виконавці мають доступ до того самого підрозділу. Для прогону використано 18.11.2026 за Києвом.

1. Під Координатором А виберіть «2026 · ІІ півріччя» у полі «Період реєстру» й відкрийте M-501. Призначте Виконавця Б. Відкрийте «Зміни виконавця за період». Ще до створення чернетки видно Координатора А, час і перехід «Виконавець А → Виконавець Б».
2. Під Виконавцем А захід відсутній у поточному перегляді. Виберіть «2026 · І півріччя». Відкрийте M-501. Панель результату одразу показує H1. Створіть чернетку, оберіть «Виконано», додайте фактичну дату 30.06.2026, опис, виміряне значення й синтетичний TXT. Подайте результат і перевірте стан «На перевірці».
3. Під Виконавцем Б виберіть H2. Список, картка та `/assignment` повертають Б. Запит результату H1 від Б повертає 404. Під координатором форма редагування плану показує базового виконавця А.

Сценарій пройшов у Chrome на ізольованій SQLite-базі. Перевірено журнал на ширині 1366 px і поданий результат H1 на ширині 390 px. Повторно пройшов сценарій повернення, заміни доказу й погодження.

## Перемикання періоду під час збереження

Використайте той самий постійний синтетичний M-501. Як Координатор А, відкрийте H2, відредагуйте назву й збережіть план. У тестовому проксі або браузері відкладіть відповідь `PATCH /api/measures/:id` на три секунди. Поки триває збереження, виберіть H1 у полі «Період реєстру».

Після відповіді реєстр залишається в H1 і показує збережену назву після оновлення списку. Якщо в H1 уже відкрито картку, вона залишається в H1. Збереження без переходу відкриває оновлену картку в тому самому періоді.
