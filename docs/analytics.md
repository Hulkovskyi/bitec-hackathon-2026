# Сигнали й панелі програми

Панель виконавця показує його заходи, строки й зауваження. Координатор бачить доступні підрозділи та чергу «Погодження». Керівник порівнює виконання за підрозділами, а аналітик переглядає поточні показники програми у своєму обсязі доступу. Дані демосценарію синтетичні.

## Показники

У розрахунках пара «захід і період» є одним зобов’язанням. Для одноразового заходу ключ періоду `once`, для постійного — `YYYY-H1` або `YYYY-H2`.

| Код | Що рахує |
| --- | --- |
| `measures` | Активні зобов’язання. Одноразові враховуються від дати початку дії, постійні та періодичні — у чинному півріччі. Контрольна дата може наставати раніше кінця періоду, як у щорічних заходів за квітень–травень. |
| `completed` | Поточні активні зобов’язання з останнім погодженим підсумком «Виконано». |
| `overdue` | Прострочені пари захід–період, включно з попередніми півріччями. |
| `overdueMeasures` | Унікальні прострочені заходи. Деталізація показує найдавніший прострочений період кожного заходу. |
| `dueSoon` | Зобов’язання зі строком від сьогодні до семи днів включно. |
| `pendingReview` | Зобов’язання з доступним результатом на перевірці. |

Частка виконання дорівнює `completed / measures`. За нульового знаменника API повертає `null`. Лічильник обраного показника дорівнює кількості рядків у всіх сторінках його деталізації.

## Правила сигналів

Дата зрізу `asOf` визначається сервером за календарем `Europe/Kyiv`. Для одноразового заходу діє планова дата. Для постійного строк дорівнює кінцю робочого інтервалу півріччя, обмеженого датами програми й початком дії заходу. Строк оцінюється для кожного періоду, який уже почався.

| Сигнал | Умова |
| --- | --- |
| `overdue` | Строк минув і за цей період немає погодженого підсумку «Виконано». |
| `due_soon` | Активний захід без погодженого повного виконання має строк сьогодні або протягом наступних семи днів. |
| `missing_evidence` | В останнього поданого, а за його відсутності в останнього погодженого результату бракує актуального файла, файл зник або перевірка цілісності не пройшла. |
| `target_not_met` | В останньому погодженому повному чи частковому результаті є виміряне значення, яке не досягло цілі індикатора з урахуванням напряму. |
| `closed_without_improvement` | Останній погоджений результат позначено виконаним, але виміряне значення не покращилося щодо базового. Правило діє для напрямів збільшення і зменшення. |

Значення індикатора округлюються до шести знаків після коми перед порівнянням. Погоджені підсумки «Виконано частково» та «Не виконано» не закривають прострочення. Чернетка нової ревізії не скасовує останній погоджений стан. Неактивний захід може мати прострочення за минулий період, але не отримує нагадування про наближення строку.

30 червня для незакритого H1 з’являється `due_soon` із залишком 0 днів. 1 липня той самий H1 дає `overdue`, а H2 має свій строк. Два прострочені півріччя одного заходу дають два періоди й один унікальний захід.

Від дати архівного зрізу офіційного синтетичного набору підрахунок строків враховує джерельні статуси. Позначка «Виконано» закриває строк одноразового заходу. Для постійних та періодичних заходів архів описує тільки вихідне півріччя та не задає датованих прострочень RF1. Чинне погодження в застосунку має пріоритет. Для інших півріч робочі строки розраховуються за планом.

Кожен сигнал показує правило, вихідні значення, пояснення та запропоновану дію. Якщо поточний сигнал посилається на результат, перехід відкриває його джерельну ревізію.

## Зріз організаторів

У розділі «Сигнали» джерело «Зріз організаторів» відтворює правила для імпортованого півріччя на дату з набору. RF1–RF5 перевіряють прострочення, наявність підтверджень, зміну показника ризику, подібність опису до назви та досягнення цілі. RF6 показує повторне перенесення заходу або щонайменше два доступні прострочення одного підрозділу. RF7a–RF7e перевіряють дати виконання й доказів, наявність пояснення, заходи впливу для високих ризиків та передчасні описи.

Для RF3 частка пройденого шляху дорівнює (факт − база) / (ціль − база). Сигнал виникає нижче 10%, включно з рухом від цілі. RF4 застосовує коефіцієнт Жаккара до множин перших п'яти літер слів від чотирьох літер. Поріг становить 60%. Число або посилання в описі виключає сигнал.

Новий імпорт зберігає довідкові значення та зв'язки джерела окремо від поточних налаштувань. Для раніше імпортованої програми сигнали, яким потрібні відсутні архівні поля, позначають використання доступних поточних довідників. Сигнали та їхні агрегати розраховуються в межах доступу користувача. Остаточне видалення записів поширюється і на їхні архівні дані.

## Управлінські рішення

Адміністратор і координатор із правами аналітики та погодження можуть зафіксувати дію, активного відповідального в доступному підрозділі й строк. Для запису потрібен актуальний сигнал. Збереження рішення створює запис аудиту в тій самій транзакції. У списку рішень зберігаються пояснення й факти сигналу на момент збереження, зокрема після його зникнення. Доступ до списку залежить від ролі та підрозділу.

## API

Потрібна сесія та `programId` у форматі UUID. Запити панелі й сигналів підтримують `departmentId`, `page` і `pageSize` та повертають `asOf`, `items`, `total`, `page` і `pageSize`. Типовий розмір сторінки 20, максимальний 100.

- `GET /api/dashboard` приймає `metric` з таблиці показників, типово `measures`. Додатково повертає `counts` і `completionRate`. Рядок містить `measureId`, `periodKey`, `code`, `title`, `deadline` та поля доступного результату, коли він є.
- `GET /api/risk-flags` приймає `source=live` (типово) або `source=official` та необов’язковий `ruleCode` відповідного джерела. Рядок містить `subjectType`, `subjectId`, `periodKey`, `ruleCode`, `sourceValues`, `explanation` і `suggestedAction`. Поточний сигнал, що посилається на результат, також має `resultId`. Архівний запит повертає `archive` з датою й періодом зрізу або `null`. Перевірка файлів виконується для поточного `missing_evidence` та загального списку поточних сигналів.
- `GET /api/measures/:id?source=official` додає `officialResult` з описом, заявленим станом, фактичним показником і назвами підтверджень за умови доступу до вихідного й поточного підрозділів. Перехід з архівного сигналу відкриває ці дані в картці заходу.
- `GET /api/risk-flag-decisions` повертає сторінку доступних рішень та `canDecide`. Підтримує фільтр `departmentId`.
- `GET /api/risk-flag-decisions/assignees` приймає ключ сигналу `programId`, `source`, `ruleCode`, `subjectType`, `subjectId`, `periodKey`. Повертає список відповідальних, поточне рішення за наявності та `signalVersion`.
- `PUT /api/risk-flag-decisions` приймає той самий ключ, `action`, `assigneeId`, `dueDate`, `signalVersion` і `version` рішення. Для першого збереження `version` дорівнює 0. Застаріла версія або змінене джерело повертають `409`.

API фільтрує записи до підрахунку та пагінації. Для виконавця додатково враховується його чинне призначення за періодом. Недоступні ревізії не розкривають ідентифікаторів, коментарів або вихідних значень. Невідома й недоступна програма або підрозділ однаково повертають `404`.

## Як перевірити

1. Запустіть чисту демобазу за [README](../README.md). В огляді Виконавця А відкрийте M-501. У Виконавця Б має бути M-502.
2. Подайте M-501 за [сценарієм погодження](workflow.md). Як Координатор А відкрийте його з черги «Погодження» та поверніть із коментарем. Перевірте зауваження в огляді Виконавця А.
3. Як Керівник А оберіть «Навчальний підрозділ 2». У другому півріччі 2026 року поточний рядок M-503 має ключ H2, а прострочений сигнал за H1 відкриває картку й результат за H1.
4. Запустіть `npm test`. Набір A–G/X перевіряє правила, обмеження доступу, відповідність деталізації лічильникам і межу 30.06/01.07. Тестові файли лежать у [застосунку API](../apps/api/test/).
